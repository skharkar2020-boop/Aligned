# lipophilic-efficiency-trap: maintainer notes

Optional maintainer notes for this task. Not shipped to the agent.

## Design summary

A hit-to-lead SAR dataset for a fictional kinase target ("Kinase X"), 30
analogs (24 generic background compounds + 6 deliberately placed archetype
compounds, `C101`-`C106`) from one scaffold. The task asks the agent to
nominate a single compound to progress, from raw replicate potency assays
(with QC-flagged failed replicates that must be excluded) and
ADME/physicochemical descriptors.

Correctly recovering the intended lead (`C105`) requires integrating
potency, selectivity, lipophilic ligand efficiency, and developability
together. No single visible column, naive sort, or (critically) the one
threshold actually disclosed in `instruction.md` recovers it alone. See
`solution/process.md` for the full generative mechanism, the six-archetype
table, and validated numbers.

## Data provenance

Generated by `data_generation/generate_data.py` (deterministic,
`hashlib.sha256`-seeded per compound/assay). The generative model has three
latent drivers: `intrinsic_fit` (genuine, logP-independent SAR),
`offtarget_idio` (independent off-target-affinity noise), and `metab_idio`
(independent metabolic-liability noise) -- the latter two exist specifically
to keep `clogp`'s relationship with off-target potency and clearance real
but non-deterministic (`r ~= 0.57-0.72`, not the ~0.99-1.0 of earlier
versions -- see "Design history" below).

- Developability thresholds (`solubility_um >= 20`, `clint_ul_min_mg <=
  45`, `papp_1e6cm_s >= 8`) are standard, disclosed literature-typical
  hit-to-lead triage bars -- the answer emerged from the generative
  mechanism, not from picking a threshold that produces it.
- The selectivity criterion used for the final nomination is
  `selectivity_index > 0` -- deliberately a natural zero-point ("genuinely
  more potent against the target than the off-target paralog"), not a
  tuned magic number like the previous design's `>= 0.6`. This matters
  because the decoy compound it excludes (`C106`) has a *negative*
  selectivity_index (-0.49) -- rejecting it doesn't require knowing any
  specific cutoff, only that a sign flip is disqualifying. It remains
  undisclosed in `instruction.md` (see below), but its exact value is no
  longer load-bearing for correctness the way `0.6` was.

## Instruction disclosure and the mechanical-shortcut test

Two rounds of empirical findings, in order:

**Round 1 (leaked diagnostic).** The first version of this task disclosed
`clogp_target_potency_r` and `clogp_offtarget_potency_r` as required
`result.json` fields. A quick single-agent trial passed on the first
attempt, and its transcript quoted the reported `clogp_offtarget_potency_r
~ 0.999` value directly as the stated reason for the nomination -- the agent
didn't need to notice the lipophilicity/off-target relationship itself, it
just read the number the task told it to compute. Both correlation fields
were removed; `result.json` now reports only `naive_top_potency_id` and
`n_developability_pass`.

**Round 2 (single-confound landscape too easy).** With the leaked diagnostic
gone, a full 3-agent x 4-trial campaign (Claude, Codex, Gemini) still went
12/12 -- every agent built the derived table and read the pattern straight
off it, since the single-confound design made `clogp` vs. off-target potency
almost perfectly linear (`r ~ 0.999`) and one compound dominated every
efficiency metric simultaneously. This motivated the six-archetype
redesign (see `solution/process.md`).

**Mechanical-shortcut validation (before finalizing the redesign).** Before
committing the richer landscape, its own disclosed contract was stress-
tested directly: does *only* the disclosed `developability_pass` threshold,
with no selectivity reasoning at all, already recover the answer by sorting
survivors on `lle`? Initially, yes -- so `C106` was added specifically to
break this: it passes every disclosed threshold and has the highest `lle`
of any developability-passer, but its `selectivity_index` is negative.
The mechanical shortcut (`developability_pass` filter + argmax `lle`, using
nothing beyond the literal instruction.md contract) now returns `C106`, not
`C105`. Recovering `C105` requires checking selectivity too -- and no exact
threshold value is needed to see that a negative selectivity_index is bad.

The general lesson across both rounds: a diagnostic or a threshold that is
disclosed *as a required, checked output field or gate* can leak the
mechanism just as effectively as disclosing the decision rule itself, even
when every individual per-row formula stays disclosed (which
`well_specified`/`structured_data_schema` require). The fix each time was to
either stop disclosing the diagnostic, or to make the underlying data
resistant to the specific mechanical shortcut the disclosed contract makes
available -- never to hide an otherwise-necessary threshold arbitrarily.

## Solution and verifier design

- `compound_metrics.csv` tolerances: 1% relative (0.02 absolute floor) --
  every derived field is simple arithmetic on clean, already-averaged
  inputs, not a numerical approximation, so a materially different method
  should not pass.
- `naive_top_potency_id` and `n_developability_pass` are checked by exact
  match against independent recomputation.
- `nominated_lead_id` is checked by exact string match against the
  verifier's own independent recomputation -- a discrete correctness check
  with no statistical margin to tune. Manually verified that all five decoy
  archetypes (`C101` naive potency, `C104` raw LLE, `C103` selectivity-only,
  `C102` conservative-but-weaker, and critically `C106` the mechanical-
  shortcut decoy) fail this check when substituted for the correct answer,
  with a comfortable margin (0.322 lle units over the nearest real
  competitor, `C102`) that is stable under an alternate, equally defensible
  averaging method (mean-IC50-then-log vs. mean-pIC50: 0.3221 vs 0.3228).

## Known constraint: Docker Hub CDN egress

This sandbox's egress policy blocks Docker Hub's CDN, so both Dockerfiles
pull from `mirror.gcr.io/library/python:3.12-slim` instead of
`python:3.12-slim` directly (confirmed byte-identical via matching manifest
digest to the upstream image).
