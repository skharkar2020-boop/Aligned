# Scientific task maintainer notes

## Data provenance

All three public tables (`pk_concentrations.csv`, `pd_response.csv`,
`subjects.csv`, identical copies in `environment/data/` and `tests/data/`) are
synthetic, generated by `../data_generation/generate_data.py` (deterministic,
closed-form Bateman-function PK model, no external network dependency, no
ODE solver). That script also writes
`../data_generation/private/subjects_ground_truth.csv`, an authoring-only
file; it is **not** copied into `environment/data/`, `tests/data/`, or either
Docker build context, and must never be.

### v1 -> v2 redesign

The task originally shipped as a simpler 2-cohort (single-dose vs. multi-dose
steady-state), 90-subject design where the verifier picked the winner via
`min(abs(single_dose_r), abs(multi_dose_r))`. That formula was itself the
thing an agent needed to reverse-engineer: a live evaluation run found Codex
simply inferred and followed the rule rather than doing genuine dose/regimen
reasoning, so the task was too easy for the wrong reason (an exploitable
verifier shape, not real PK/PD difficulty).

v2 is a full redesign, built iteratively against real generated-data
statistics rather than assumed parameters:

- **4 cohorts** (dose level low/high x regimen single/repeated, 8 subjects
  each, 32 total) instead of 2, with `dose_mg` and `tau_hr` (12h, 7 doses)
  making dose and regimen independently variable.
- **M1 is the decoy, M2 is the true driver** (inverted from v1's M1-is-driver
  design) via a closed-form PK model: M1 fast-forms/fast-clears (Tmax ~1.4h,
  t1/2 ~1.7h, high Cmax, negligible accumulation), M2 slow-forms/slow-clears
  (Tmax ~9-11h, t1/2 ~11.6h, lower Cmax, real accumulation, ratio ~3.5x vs.
  M1's ~1.0-1.3x). PD is generated as a pure function of M2's sustained/lagged
  exposure (AUC8-24 single-dose, steady-state AUCtau repeated-dose) with no
  direct dose term; M1's naive correlation with PD is a Simpson's-paradox
  artifact of both M1 and PD independently scaling with administered dose.
- **One moderately-salted influential subject** (M1 amplitude x3.0, an
  independent noisy PD elevation, not a cartoonish 4x+fixed-bump outlier)
  makes M1's naive correlation *fragile* under leave-one-out without being
  visually obvious by inspection.
- Per-subject independent log-normal noise on formation/elimination rates
  (not merely a shared curve scaled by dose) gives genuine inter-individual
  heterogeneity: M1/M2 Cmax coefficient of variation 0.67/0.82, M1-to-M2
  crossover time ranges 3.0-60.9h across subjects (27/32 subjects show a
  crossover at all; 5 do not), subject-level M2 accumulation ratio 1.66-5.61
  (every one of the 16 repeated-dose subjects individually exceeds M1's own
  ratio, not just the population mean).
- 13 PK time points per subject/analyte (`0.25,0.5,1,2,4,6,8,10,12,16,24,
  36,48h` since-dose for single-dose subjects; `0,0.25,0.5,1,2,4,6,8,12,16,
  24,36,48h` since-last-dose for repeated-dose subjects, including a
  genuine observed 0h trough) -> exactly 32 x 3 x 13 = 1,248 raw PK rows.
- A required patient-level deliverable, `subject_metrics.csv` (96 rows: 32
  subjects x 3 analytes), in addition to the population-level `result.json`
  — see "Solution and verifier design" below for the full field list and
  the integration-origin/time-coordinate conventions.

Multiple rounds of author feedback during this redesign each surfaced a real
generator defect, fixed in order:

1. **Simpson's-paradox mechanism didn't reproduce quantitatively at first**
   (M1's naive/pooled correlation was far weaker than M2's, the opposite of
   the intended trap) — root cause was pooling single-dose and repeated-dose
   subjects together on a raw-AUC basis, which let M2's much larger
   steady-state accumulation swamp the dose-driven signal M1 was supposed to
   win on. Fixed by scoping the naive/adjusted metrics to comparable
   exposure windows (AUC0-6, single-dose cohort) and retuning per-analyte
   IIV (M1: tight formation/elimination noise so its exposure tracks dose
   cleanly; M2: independently randomized formation-rate noise so its Cmax
   doesn't closely predict its own sustained-exposure AUC — the intended
   Cmax-vs-AUC decoupling).
2. **Leave-one-out fragility didn't show up** with 2 salted subjects (at
   n=16, removing 1 of 2 still leaves the other in place) or with a
   too-extreme 4x/fixed-bump salt (full r barely moved, because the salted
   subject sat inside the natural cloud rather than genuinely extending the
   trend). Fixed with exactly 1 salted subject, and by explicitly
   constructing its PD value to extend the dose-driven trend (not just add
   independent noise on top of its natural baseline).
3. **Parent occasionally out-scored M1 on raw Cmax/AUC0-6** after an
   unrelated dose-ratio change. Fixed by reducing `PARENT_SCALE_PER_DOSE`
   (1.10 -> 0.70) — a pure magnitude change; it does not move parent's
   correlation with PD (uniform scaling doesn't change correlation), and
   parent still narrowly edges M1 on the naive correlation fields by design
   (both are decoys; deliberately not forced into a particular order beyond
   what the mechanism produces).
4. **Individual subject-level accumulation ratio turned out not to be
   computable from the data actually collected** (repeated-dose subjects are
   only sampled around their final dose, with no subject-specific
   first-dose reference) — resolved by keeping accumulation ratio a
   population/cohort-level `result.json` field only, not a per-subject
   `subject_metrics.csv` column, rather than manufacturing an individual
   ratio against an unrelated cohort mean.

Final validated population-level metrics on the shipped dataset (see
`solution/process.md` for the full table and mechanism writeup):

| metric | parent | M1 | M2 |
|---|---:|---:|---:|
| naive_pd_r | 0.684 | 0.667 | 0.408 |
| cohort_adjusted_pd_r | -0.117 | 0.119 | **0.609** |
| repeated_dose_pd_r | 0.807 | 0.682 | **0.968** |
| lagged_pd_r | 0.760 | 0.727 | **0.927** |

M2 dominates all three disclosed decision criteria by 0.16-0.49; parent
edges M1 on the naive metric by a trivial 0.017 (both decoys, not tuned to a
particular order). M1's naive leave-one-out: 0.667 -> min 0.621 (fragile).
M2's lagged leave-one-out: 0.927 -> min 0.905 (robust).

Re-run the generator to reproduce: `python3 data_generation/generate_data.py`
from the project root writes `data_generation/public/*.csv` (copy these into
`environment/data/` and `tests/data/`) and
`data_generation/private/subjects_ground_truth.csv` (authoring-only, never
ships).

## Container contract

The runtime Dockerfile builds explicitly for Linux/amd64, copies only
`environment/data/`, creates the non-root `agent` user, and has no networked
package or agent-bootstrap step at runtime. `environment/wheels/` vendors
both the solution's runtime dependencies (`numpy==2.1.3`, `pandas==2.2.3`,
and their transitive deps) and the verifier's dependencies (`pytest==8.4.1`,
`pytest-json-ctrf==0.3.5`, and transitive deps), since the Nexus sandbox runs
one shared image for both the agent and the verifier and ignores
`[verifier].environment_mode`. `tests/wheels/` carries the same combined set
for the optional local two-image `tests/Dockerfile` fixture, which is not
used by submission.

## Solution and verifier design

### Deliverables

`solution/solve.py` produces two output files:

- **`subject_metrics.csv`** (96 rows: 32 subjects x 3 analytes, one row
  each): `cmax`, `tmax_hr`, `auc0_6`, `auc0_12`, `trough` (repeated-dose
  subjects only), `relevant_auc`. Two conventions apply throughout, stated
  identically in `instruction.md`, `solution/solve.py`, and
  `tests/test_outputs.py`:
  - **Time coordinate**: `pk_concentrations.csv`'s `time_hr` is absolute
    time since each subject's first dose. `tmax_hr` and the `auc0_6`/
    `auc0_12` window boundaries are relative to that subject's *most recent*
    dose (`time_hr - last_dose_time`, `last_dose_time = (n_doses-1)*tau_hr`)
    — the standard clinical-PK convention, and the only way `tmax_hr` is
    comparable between a single-dose and a 7th-dose steady-state subject.
  - **Integration origin**: every AUC uses the trapezoidal rule exclusively.
    A window starting at time-since-last-dose = 0 is anchored with a
    synthetic `(0, 0.0)` point when no sample exists exactly there (true for
    every single-dose subject, whose first visible sample is 0.25h;
    concentration is 0 at the moment of a dose). Repeated-dose subjects have
    a genuine observed 0h trough sample, so no synthetic point is used
    there. `relevant_auc` is AUC8-24 for single-dose subjects and the
    steady-state AUCtau (== `auc0_12` for that row, since `tau_hr = 12`, by
    definition not coincidence) for repeated-dose subjects.
  - Individual accumulation ratio is **not** a `subject_metrics.csv` column:
    repeated-dose subjects are only sampled around their final dose, with no
    subject-specific first-dose reference, so a per-subject ratio would
    necessarily divide by an unrelated cohort mean. Accumulation ratio stays
    a population/cohort-level `result.json` field.
- **`result.json`**: for each of `parent`/`M1`/`M2` — `cmax`, `tmax_hr`
  (single-dose means), `naive_pd_r` (AUC0-6 vs. PD, single-dose, unadjusted),
  `cohort_adjusted_pd_r` (AUC0-12 vs. PD, centered within each of the 4
  dose x regimen cohorts — equivalent to controlling for dose, regimen, and
  their interaction), `repeated_dose_pd_r` (relevant_auc vs. PD,
  repeated-dose subjects only), `lagged_pd_r` (relevant_auc vs. PD, all
  subjects), `naive_min_loo_r` / `lagged_min_loo_r` (leave-one-out minima on
  the naive/lagged bases); plus `M1_accumulation_ratio` /
  `M2_accumulation_ratio` (population-level, matched across dose levels);
  plus `nominated_species`.

### Verifier

`tests/test_outputs.py` independently recomputes the entire pipeline from
its own copy of the data (`tests/data/`, byte-identical to
`environment/data/`) and checks:

- `subject_metrics.csv` contains exactly the 96 expected `(subject_id,
  analyte)` rows, each present once (no missing/duplicate/extra);
- every subject-level field is within **1% relative tolerance (or a 0.05
  absolute floor near zero)** of the verifier's own recomputation — tight,
  because the task specifies the trapezoidal rule exclusively, so a
  materially different integration method should not pass; `tmax_hr` (a
  discrete argmax over a fixed sample grid, not a numerical approximation)
  must match **exactly**;
- `result.json` has the correct schema and finite, in-range values;
- every reported population-level aggregate matches independent
  recomputation (0.02 absolute tolerance for correlation fields, 5% for
  accumulation ratios — two compounded subject-level tolerances);
- the nominated species' recomputed `cohort_adjusted_pd_r`,
  `repeated_dose_pd_r`, and `lagged_pd_r` each exceed the best of the other
  two candidates' corresponding values by at least **0.05** — a
  multi-criterion dominance check (not a single formula), chosen well below
  the >=0.16 margin M2 achieves on every one of those three criteria in the
  shipped dataset (0.49 on the adjusted criterion alone). This design is a
  direct response to the v1 verifier's `min(abs(single_dose_r),
  abs(multi_dose_r))` formula being reverse-engineered by an agent rather
  than reasoned to: v2 requires leading on three independently-disclosed,
  differently-computed criteria simultaneously, not matching one hidden
  arithmetic expression.

Manually verified both failure directions: a `"M1"` nomination and a
`"parent"` nomination each fail the dominance test on `cohort_adjusted_pd_r`
by roughly 0.5 (far beyond the 0.05 threshold) against the recomputed
values, while the Oracle's `"M2"` nomination passes all five tests.

## Local commands

From the repository root:

```bash
python3 scripts/validate_scaffold.py
./harbor_runner.py task --no-remote --smoke-test
```

For a fast authoring check with an already-installed host agent, run one local
trial without Workbench or Modal:

```bash
./harbor_runner.py task --quick --quick-agent codex   # or claude
```

Quick evidence is kept under `harbor-jobs/` and
`trajectories/quick/<run-id>/`; it is separate from the three-agent campaign
archive.

To verify the vendored dependencies without an index:

```bash
python3 .agents/skills/task-fixer/scripts/vendor_offline_dependencies.py \
  --task task --out task/environment/wheels --python-version 3.12 --verify
python3 .agents/skills/task-fixer/scripts/vendor_offline_dependencies.py \
  --task task --out task/tests/wheels --python-version 3.12 --verify
```

After a successful multi-agent run, the vendored runner writes its Oracle,
agent trajectories, and combined summary directly under the project-level
`trajectories/` folder. Run the trajectory review described in the root
`README.md` against that folder.

## Known open item (resolved)

The Docker smoke test (`./harbor_runner.py task --no-remote --smoke-test`)
previously could not be run: the authoring session's egress policy denies
outbound access to Docker Hub's blob CDN (`production.cloudfront.docker.com`,
403 policy denial on `CONNECT`), so `python:3.12-slim` could not be pulled in
that environment, even though Docker Hub's registry/auth API
(`registry-1.docker.io`) itself was reachable.

Fix: both `environment/Dockerfile` and `tests/Dockerfile` now pull the base
image from `mirror.gcr.io/library/python:3.12-slim` instead of
`python:3.12-slim` directly. `mirror.gcr.io` is Google's public read-through
cache of Docker Hub — it serves the identical image content (confirmed by
matching manifest digest,
`sha256:09f7da3bc104798d0afb40bc08d23ab2da20a76130cec1f2ef170848f5d85217`,
against the upstream `python:3.12-slim` manifest) through a CDN this
environment's egress policy does not block. This is a build-time base-image
source change only; it does not affect the runtime contract (the built image
still has no networked package or agent-bootstrap step at runtime).

With that change, `./harbor_runner.py task --no-remote --smoke-test` now
builds and runs successfully end-to-end: `solve.sh` exits 0 and all three
`tests/test_outputs.py` checks pass (schema/finite-value validity, the
nominated-species dominance margin, and the reported-association integrity
check) inside the actual container, not just via the host Python
interpreter used for earlier validation.
